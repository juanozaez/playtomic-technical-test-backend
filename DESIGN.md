# Design

## Three pillars
The solution proposed is based on three pillars:

-   Focus on the domain
-   Decouple the PSP/Repositories from the domain
-   Consider high availability in the architecture to avoid collisions

### Focus on the domain

The main actor is the `Wallet` and as such, it cannot remain in an inconsistent state. For that reason all the logic and business invariants related to its operations (top up, refund...) are/will be included and verified inside the Wallet class.

This is achieved by implementing a Domain Driven Design (DDD) approach, where the Wallet is treated as an Aggregate Root, responsible for maintaining its own consistency. For example:

* When topping up, the Wallet ensures that the amount is positive and that the resulting balance remains within acceptable limits (if any).
* When spending, the Wallet should verify that there are sufficient funds.

This approach ensures that the application's core business logic is robust and independent of external factors like the payment service provider (PSP) or the database.
We also avoid ending up with an [anemic domain model](https://martinfowler.com/bliki/AnemicDomainModel.html)

### Decouple the PSP/Repositories from the domain

To avoid tight coupling with the specific PSP (e.g., Stripe), an interface (`PaymentClient`) is defined in the domain layer. This interface represents the abstraction of a payment service.

The actual implementation of this interface (e.g., `StripePaymentClient`) resides in the infrastructure layer. This allows us to:

* Easily switch to a different PSP in the future by providing a new implementation.
* Test the domain logic in isolation by using a fake implementation of the `PaymentClient`.
* Maintain a clean separation of concerns, keeping the domain layer focused on its core responsibility.

### Consider high availability in the architecture to avoid collisions

To handle concurrent requests and maintain data consistency in a high-availability environment, the following strategies are considered:

* **Pessimistic Locking:** When performing operations that modify the Wallet's balance, a pessimistic lock (`SELECT ... FOR UPDATE`) is acquired at the database level. 
This prevents other transactions from modifying the Wallet's state until the current transaction completes, avoiding race conditions. 
While this can impact performance under high contention, it guarantees strong consistency, which is crucial for financial transactions.
* **Idempotency:** To handle potential retries from clients (e.g., due to network issues), operations like topping up should be designed to be idempotent. 
This can be achieved by using unique transaction identifiers generated by the client and checking for their existence before processing a transaction.

These considerations aim to build a robust and scalable system that can handle the demands of a real-world wallet service.

## Technical considerations

### Structure
The proposed package structure follows DDD conventions and hexagonal architecture, with three different layers 

The proposed package structure follows DDD conventions and hexagonal architecture, with three different layers:

* **Domain:** This layer encapsulates the core business logic and domain model (entities, value objects, aggregates). It is completely independent of any infrastructure concerns and defines the interfaces (ports) for interacting with external systems (e.g., repositories, payment gateways).
* **Application:** This layer orchestrates the domain objects to fulfill specific use cases or business processes. It does not contain any business logic itself but rather coordinates the work of domain services and entities.
* **Infrastructure:** This layer implements the interfaces defined in the domain layer, providing concrete implementations for interacting with databases, external APIs, message queues, and other external systems (adapters).

This layered structure promotes separation of concerns, testability, and maintainability.

### Testing strategy

The testing strategy is structured around three key types of tests:

* **Behavior Tests:** Verify the application's core business logic, focusing on use cases and the interaction between the application and domain layers.
* **Acceptance Tests:** Validate the end-to-end functionality of the system, simulating user workflows and interacting with the application through its external interfaces.
* **Integration Tests:** Ensure the correct interaction of the application with external dependencies, such as database and payment gateway.
